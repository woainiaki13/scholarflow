# ScholarFlow：从功能集合收成一条学习流程

这次调整针对产品本身的衔接。原来的上传自动化确实能生成资料，八个学习工具也能运行，但用户完成一步后，还要自己找下一页、重新决定来源并复制问题。结果历史按工具排列，很难看出同一份课件上的理解是怎样变化的。

现在以一份来源资料作为工作区：

**选择或上传资料 → 自动形成学习包 → 设定学习目标 → 解释与验证 → 保存理解变化 → 小组继续使用。**

同一份资料的原文、学习包、目标、完成记录和反思共同构成这条学习线。八个功能是这条线中按需调用的动作，不要求用户依次跑完八个功能。

## 现有技术架构怎样服务这条主线

这次统一的是网页中的来源工作区和交接关系，没有重写后端执行管线。各段仍使用已经接通的服务：

| 处理环节 | 当前真实执行路径 |
| --- | --- |
| 网页上传与拆分 | 浏览器读取 PDF/PPTX/TXT/Markdown 的文字并分段；`/api/originals` 将原始文件存入 BUCKET。 |
| 自动生成学习包 | 浏览器逐段调用 `/api/ingest`；后端上传到 Dify 并调用已发布的 intake 工作流，浏览器合并各段的笔记、证据卡和引用信息。 |
| Dify 格式异常恢复 | 现有路径在可恢复的短文字片段发生结构格式错误时，使用已有 DeepSeek 重建笔记和匹配卡；它不会凭空恢复引用元数据。 |
| 按需学习工具 | 网页的模型工具通过 `/api/analyze` 直接调用现有 DeepSeek 网关，再匹配原文证据。它们没有全部改成执行 Dify 的八工具工作流。 |
| 来源恢复 | 浏览器对当前来源执行原文精确匹配，不调用模型；文本行数不冒充 PDF 页码。 |
| 小组共享与原件 | `/api/shared` 保存来源、学习包和完成记录到共享数据库；BUCKET 保存文件，`/api/files/…` 读取相应小组的原件。 |

主流程的编排在前端：选择来源、保存目标、准备下一项输入、调用对应服务、保存来源范围和前序关联、展示可复用成果。密钥仍在现有后端服务中，没有放到 GitHub 网页。Google Drive 的独立定时入口没有在本轮接入这条小组数据链。

## 用户怎样走下去

1. 在首页上传资料，或继续小组已有的资料。文件读取、长文分段、笔记、原文匹配的证据卡、引用信息保留和共享保存由现有自动化完成。
2. 对当前资料写一个学习目标，例如“检查零 beta 的对冲是否也消除了公司特有风险”。点击保存后，这个目标成为小组可见的资料目标。
3. 从目标选择合适的动作。解释概念时用误解日记或概念重建；检验判断时用证据地图、方法边界或来源恢复；准备成果时再用作业罗盘、复现配方或版本影响。
4. 完成结果保留当前来源、目标及上一条记录。后续动作沿用已有的输入，避免每次重新开始；需要用户写的解释、作业要求和方法条件仍由用户提供。
5. 查看同一资料的学习记录，保存具体反思。组员通过同一邀请链接读取已完成的结果与反思，再继续自己的练习。

## 八个功能在主线里的作用

| 用户当前的问题 | 可用动作 | 得到的具体结果 |
| --- | --- | --- |
| 我真的理解了吗？ | 误解日记、概念重建 | 原解释与反馈、概念关系与适用条件 |
| 这句话有依据吗？ | 证据地图、来源恢复 | 支持、反例、未解决证据，及可定位的原文 |
| 这个方法能用于这里吗？ | 方法边界、复现配方 | 已知条件、冲突、未知信息，以及未执行的步骤与参数框架 |
| 怎样把理解变成可用成果？ | 作业罗盘、版本影响 | 明确要求的缺口、修改影响及建议修订内容 |

这些动作不等于固定流水线。例如，仅复习定义时可以在误解日记后保存反思；需要写作业时才进入作业检查。首页应让用户继续当前资料的学习线，工具列表作为可选入口。

## 数据怎样接起来

- **Source ID** 继续作为原始资料、学习包和学习记录的关联点。
- 当前资料的 `learning_goal` 通过既有 `source` 共享记录保存；不新增独立存储服务。
- 新完成的记录带 `workflow={source_id, selected_source_ids, goal, parent_run_id}`。这里的目标是运行时快照，之后修改目标不会改写已有结果。只有用户从明确的“继续”动作进入下一项时才建立前序关系；直接开始一个任务不因时间先后就被当成旧结果的延续。
- 一次工具调用只发送当前选择的资料，避免将整个小组资料库混入当前问题。
- 每份资料的表单、概念与关系草稿分别保存在当前设备的 `learningDrafts`。未提交草稿不加入共享记录。
- 已完成的任务输入、结果和明确保存的反思继续通过现有 `/api/shared` 接口同步。接口按记录存储 JSON，新增的关联字段会一并保存，不需要数据库迁移。
- 旧记录保留原来的来源快照。多来源结果可以从它涉及的资料中查到，但需标记原来使用的是多个来源，不能把旧的全库分析改称成一次单资料分析。

## 哪些工作自动完成，哪些需要学习者参与

**系统自动完成：** 上传后的文件保存、文字读取与分段、调用现有 Dify/DeepSeek 处理、笔记及证据整理、摘录匹配、引用已知信息保留、结果保存与小组同步。用户选定当前资料后，后续调用自动沿用该资料，完成记录自动保留来源及上一步关联。

**学习者参与：** 提出学习目标、写自己的解释、描述研究设计、提供真实作业要求、判断是否需要下一项工具，以及保存自己的反思。系统不需要逐条人工审批才保存结果，但模型反馈也不等于教师评分或学习掌握证明。

## 已有实现的边界

网页上传处理期间需要保持页面打开。图片、复杂图表、公式、扫描件和 PPTX 演讲者备注可能不能从文字提取中完整获得。不能确认的 DOI、引用字段或页码继续明确标记缺失。

拥有者的 Google Drive 定时入口仍是独立通道：它不会自动把文件导入当前公开小组的共享资料库。这次前端衔接不会把它描述成已经完成的跨通道同步。Dify 管理链接和 Drive 配置属于设置，不能替代学习者的主流程。

同一资料暂时只有一个共享的当前学习目标；它不是多课题项目管理系统。完成记录保留运行时目标，旧结果可以继续追溯。

## 验证方法

`work/verify_learning_pipeline.mjs` 从现有金融演示组只读获取真实来源及保留结果，然后在隔离的本地 API 存储中验证网页衔接。它不调用真实模型，也不向公开演示组写入测试资料。

验证覆盖来源切换后的草稿保留、仅发送当前来源、结果的目标与前序记录关联、跨来源结果隔离、共享目标与本地草稿的区分、第二浏览器读取、手机布局及页面脚本错误。实际运行结论与画面保存在 `outputs/pm/pipeline-verification/`；这些属于前端和传输验证，不能冒充新增的模型准确性实验。

本次最终隔离网页验证通过 30 项具体行为检查，没有发现页面 JavaScript 错误。已有资料的小组在首次载入后直接显示学习主线，上传区域折叠。桌面与 390px 手机页面均保留完整的学习主线；新浏览器读到了共享目标和已完成记录的关联，同时没有收到另一来源仍未提交的草稿。学习简报下载也保留了所选资料的目标与成果，没有混入另一资料的结果。

删除当前资料后，页面正确切换到剩余资料，并恢复剩余资料原有的问题和草稿；被删除资料的输入没有覆盖另一份资料。共享删除也没有误删剩余资料或其历史。

既有 Worker 的 SQLite 存储测试通过 7 项，其中新增的往返测试确认 `source.learning_goal` 及历史记录中的 `workflow.selected_source_ids`、`parent_run_id` 经数据库保存后能被另一成员读取。测试使用隔离的内存数据库。

## 任务式入门与使用记录补充

当前首页以 **Start revising this lecture** 引导一次真实练习：从当前学习包选择问题、自己解释、提交反馈、回原文检查，再手写保存修正后的理解。七个其他工具保留在可选入口。资料下方新增学生亲自填写的使用记录，未测量时间不当作零；完成记录按独立 ID 小组同步，未提交草稿留在本地。

本轮也修正了跨分段重复摘录的页码问题。合并学习包及读取旧学习包时，用整份来源重新匹配；多个候选不标为唯一页码。原金融演示 C014 实际候选为物理 PDF 第33和36页，历史记录中16张唯一页码应更正为15张单页候选、4张多页候选。原始运行日志和录像保留不改。

定向刷新入口位于 **Share group → Refresh display cache**，保留资料、历史、未提交草稿和待同步写入。Google Drive 的独立通道边界保持原状。完整技术说明见 [任务式入门更新](task-guide-update.md)。
